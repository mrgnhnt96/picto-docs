Errors

How an uncaught error starts a recording or bounds the one already running, what the capture window around the error keeps, and where Picto stands down.

An uncaught error is the one thing that starts a recording without your app asking. If a session is already recording, the error decides how much of it is uploaded and when it ends. You don't set anything up for this: Picto.setup installs the error hooks.

Which errors Picto sees#

Picto.setup adds a handler to FlutterError.onError (errors during build, layout and paint) and to PlatformDispatcher.instance.onError (errors from async code). It chains onto any handler already installed, so your own handlers and crash reporter still run, and Picto doesn't mark any error as handled.

On the web, Flutter reports uncaught async errors as the browser's window error event, so Picto listens for that too. It acts only on errors thrown by Dart, and only reads the event. In a WebAssembly build the browser exposes nothing of the Dart error, so the captured exception has the type WebAssembly.Exception, a fixed message and no stack trace, and only the first such error in a run starts a session. To keep the details, run your app inside runZonedGuarded and pass what it catches to PlatformDispatcher.instance.onError.

When nothing is recording#

From Picto.setup on, whenever the app is in the foreground and no session is live, Picto keeps a rolling in-memory buffer of about the last errorWindowBefore (30 seconds by default) of the screen. This pre-roll has no session_id, is never written to disk and never uploads on its own. Picto.isRecording is false while it runs, and startRecording() discards it.

When an uncaught error fires with nothing recording, Picto turns the pre-roll into a session on the spot. The replay opens about errorWindowBefore before the error. That session then follows the capture window like any other.

This happens even on a run that sampling declined, because a run nobody was watching is the case it exists for. At a sampling rate of 0, error sessions are the only sessions you get. Error sessions also don't count toward maxNewSessionsPerHour and are never refused by it.

One session per error#

An uncaught error buys one session, not recording for the rest of the run. When the app returns from the background afterwards, Picto doesn't start another session; it runs only the pre-roll. To keep recording after an error, call Picto.startRecording().

Picto remembers each error it has started a session for, by its type, message and the top six frames of its stack, until the app restarts. The same error firing again later doesn't start another session. A different error does. Picto remembers up to 256 errors and forgets the oldest past that.

When a session is recording#

An error during a live session is recorded into that session; it never starts a second one. The first error of the session opens its capture window. Later errors are recorded too, but don't move or extend the window.

The capture window#

A session with an uncaught error doesn't upload whole. It uploads a window around the session's first error.

Before the error, the window keeps at least errorWindowBefore. It starts at a mark Picto takes every 5 seconds, so the real lookback is between errorWindowBefore and errorWindowBefore plus 5 seconds. If the error came earlier than that in the session, the window starts at the beginning of the session.

After the error, the session ends and uploads at whichever comes first:

  • errorWindowAfter (30 seconds by default) passes;
  • the app goes to the background;
  • you end the session.

The timer is a ceiling, and going to the background usually gets there first. The session uploads once, whichever wins.

The replay's timeline starts at the window, not at the session's start. Record five minutes, throw at the two-minute mark, and the replay runs about one minute, with the error about 30 seconds in. A short replay of a long session with hadError is the window working, not a lost recording.

While the window is open, the segment doesn't split at maxRecordingDuration.

After the window closes#

When the window closes, Picto uploads the session and goes back to the pre-roll, so the next error gets its full lookback too. No session starts because a window closed.

If your app called startRecording(), recording resumes the next time the app returns to the foreground, as a new session at sequence 0. The errored session's id is retired, even when going to the background is what closed the window. Until then only the pre-roll runs. Call startRecording() to resume sooner. A resumed session counts toward maxNewSessionsPerHour.

An error in the background#

Nothing is drawn in the background, so the useful window is the one before the user left. When the app goes to the background, Picto keeps the last errorWindowBefore in memory: the pre-roll if nothing was recording, or the end of your session if something was. Your session still ends and uploads as usual.

An error thrown in the background, such as from a timer or a push handler, turns what was kept into its own session with a new session_id. The replay opens about errorWindowBefore before the app left and ends with the error. It uploads straight away, since there is no after-window to wait for. Returning to the foreground discards what was kept.

When there is no lookback#

An error that fires before Picto has finished setting up, or after the app left with nothing to keep, still starts a session, but the replay opens on the error. The first time this happens in a run, the console says so: 

[Picto] started a recording for an uncaught error, and this one has NO before-window: nothing was capturing when the error fired, so the upload begins AT the exception instead of 30s in front of it. errorWindowBefore can only keep bytes that were already captured, and picto only keeps them after setup: either the error fired before picto finished setting up, or the app left before there was anything to keep. Said once per process.

The number is your errorWindowBefore, so the message also confirms the value reached the SDK.

Change the window#

Pass errorWindowBefore and errorWindowAfter to Picto.setup:

Picto.setup(
  apiKey: const String.fromEnvironment('PICTO_API_KEY'),
  appVersion: '1.0.0',
  errorWindowBefore: const Duration(minutes: 2),
  errorWindowAfter: const Duration(seconds: 10),
);

Both apply to every session in the app run, and a negative value is treated as zero. The 5-second mark interval is fixed.

  • A longer errorWindowBefore means larger error uploads and a larger pre-roll in memory. It doesn't change what is captured.
  • A longer errorWindowAfter delays the upload of a session that errors and keeps running in the foreground. A shorter one shows less of what happened after the error.

Where Picto does nothing#

Under a test binding, such as testWidgets, flutter_driver or integration_test, Picto isn't the live binding and can't record anything. It starts no error session, runs no pre-roll and arms no timer. See Testing.

If starting a session for an error fails, Picto doesn't throw from inside the framework's error handler. It prints this instead: 

[Picto] failed to start a recording session for an uncaught error: <error>

What you see in the dashboard#

The session has hadError set to true and a captured exception with its type, message and stack trace. See Finding & Watching Sessions.
