Sessions CLI & MCP

Let a coding agent list your recorded sessions, read their timelines, and render video or still frames with picto:sessions and picto:mcp.

dart run picto:sessions and dart run picto:mcp give a coding agent read access to your recorded sessions, so it can see what a user did instead of guessing.

Both ship in the picto package, so any project that depends on it has them. They read exactly what your account can see in the dashboard, and never change anything.

Before you start#

You need:

  • A project that depends on picto (see Quick Start).
  • A Picto account with a password. An account made from a sign-in link has none: open Account in the dashboard and click Add a password (see Account & Team).
  • An organization with a plan or a running invite trial. Agent access is on every plan.

Sign in#

Run login once in a terminal:

dart run picto:sessions login

It asks for your email and password (the password isn't echoed) and saves the session to ~/.config/picto/credentials.json, readable only by you. $XDG_CONFIG_HOME/picto is used instead when that variable is set. Pass --email to skip the first prompt. --password also exists, but the prompt keeps your password out of your shell history.

The saved session renews itself while it's in use, so it lasts as long as a picto:sessions command runs at least once a week. Once it lapses, every command exits with code 3 and says to run dart run picto:sessions login.

logout ends the session on the server as well as removing it from your machine:

dart run picto:sessions logout

For CI, pass --token <token> or set PICTO_TOKEN to use a bearer token instead of the saved session. Nothing is saved or renewed.

Commands#

Every command except login, logout and list takes a session ID, as list prints it.

CommandWhat it does
listRecent sessions, newest first
show <id> One session: its segments, metadata, and every exception, tap cluster and frozen frame with its time in the session
timeline <id> Every event in the session in order, each with its session time. No images, so it's the fastest way to read a session.
video <id> Renders an .mp4 , with a .manifest.json and a .captions.vtt beside it
frames <id> Renders PNG stills into a directory, with a manifest.json
download <id>Saves one segment's raw recording bytes

timeline, video and frames render on Picto's servers and wait for the result, for up to 10 minutes. Rendered files stay on the server for 24 hours.

Options for list#

OptionDefaultEffect
--limit <n>20Sessions per page
--before <cursor> None The next page. A page that has more prints the cursor (nextBefore in JSON).
--has-errorsNoneOnly sessions with an exception
--has-rage-tapsNoneOnly sessions with a rage tap
--platform <name> None Only ios, android, macos or web
--client-app <id>NoneOnly one client app

Options for timeline, video and frames#

OptionDefaultEffect
--start <time>, --end <time> Whole session A window in session time: 1:03, 63s or 63000 (milliseconds)
--keep-idle Off Keep idle stretches (see Idle stretches are cut)
--max-width <px> 720 Downscale frames to at most this width
--no-pointersOffDon't draw tap ripples

video also takes -o, --output <file> (default picto-<id>.mp4) and --fps <n>, 1 to 30 (default 10).

frames also takes -o, --output <dir> (default picto-<id>-frames), --every <interval> for the periodic frames (default 1s), and --no-event-frames to drop the extra frame it otherwise takes at each tap, screen change and error.

Options for download#

download takes -o, --output <file> (default picto-<id>-<sequence>.bin) and --sequence <n>. A session with more than one segment needs --sequence; without it the command fails with a message listing the segment numbers.

Read the output#

On a terminal the commands print tables and summaries. When stdout isn't a terminal, which is how an agent's shell tool runs them, they print JSON. --json forces JSON anywhere.

Failures are JSON too, under an error key with exitCode and message, and the exit code tells an agent what to do next:

Exit codeMeaning
0Success
1 Something failed. The message says what, including an hourly limit or a failed render.
2The command was used wrongly
3 Not signed in, the session expired, or access was refused. Sign in again.
4No such session, or not one this account can see
5 The session's organization has no plan or invite trial. The error has code: "plan_required" and an upgradeUrl . Signing in again won't help; choosing a plan will.

Connect the MCP server#

If your agent speaks MCP, dart run picto:mcp offers the same commands as tools, over stdio. It uses the saved sign-in and never asks for a password, so run dart run picto:sessions login in a terminal first.

For Claude Code, run this from your app's project directory, the one whose pubspec.yaml depends on picto: 

claude mcp add picto -- dart run picto:mcp

Most other clients read an mcp.json like the following. dart run picto:mcp has to start inside a project that depends on picto, so set cwd to your app's directory: 

{
  "mcpServers": {
    "picto": {
      "command": "dart",
      "args": ["run", "picto:mcp"],
      "cwd": "/path/to/your/app"
    }
  }
}

If your client has no cwd setting, use "command": "sh" with "args": ["-c", "cd /path/to/your/app && dart run picto:mcp"].

The tools mirror the commands:

ToolSame asParameters
list_sessions list limit , before , has_errors , has_rage_taps , platform , client_app_id
get_sessionshowsession_id
get_timeline timeline session_id, start, end, keep_idle
render_video video session_id , start , end , keep_idle , output , fps , max_width , pointers
render_frames frames session_id , start , end , keep_idle , output , every , event_frames , max_width , pointers , include_images , image_max_width
download_recording download session_id, sequence, output

render_frames with include_images: 4 also returns four of the frames in the result, evenly spread and downscaled to image_max_width (480 by default), so the model can look at them directly. The most it returns is 8.

Renders and downloads go to a picto-mcp folder in the system's temp directory unless a call passes output. To change that folder, start the server with --output-dir <dir>. Every result gives absolute paths.

PICTO_TOKEN works here as it does for the CLI. When nobody is signed in, every tool returns an error saying to run dart run picto:sessions login.

Idle stretches are cut#

timeline, video and frames skip idle stretches by default, the same way the dashboard's Skip idle does: any quiet gap longer than 5 seconds is cut down to its first 5 seconds. The blank stretch before the app's first paint is always cut, even with --keep-idle.

Because cuts make output time differ from session time, every render says so:

  • A note on stderr, and as idleNote in the JSON result, says how many stretches were cut and how much time they covered.
  • The manifest lists each cut under idle.skipped with its start, end and reason (idle or before_first_paint), and idle.savedMs totals them. segments maps output time back to session time.
  • Every event in the manifest has a sessionMs and an outputMs. outputMs is null for an event inside a cut.
  • captions.vtt has a cue at each cut, so a model watching the video sees it too.

When an agent quotes a time back to you, it should use sessionMs, which matches the dashboard's replay timeline.

A render that would be too long, or produce too many frames, fails with a message saying to narrow the window with --start and --end. A window that was entirely idle fails too, and the message says to re-run with --keep-idle.

Missing images in a render#

Renders draw your app's bundled images from the assets you uploaded with dart run picto:upload_assets (see Uploading Assets). An image that can't be fetched doesn't fail the render. It's left out, and the manifest lists it under warnings with its reference and a message. video and frames also print a warning: line for each on stderr.

When an agent sees an empty space where it expected something, it should check warnings before deciding the app drew nothing there.

Example workflow#

Say a user reports that checkout "sometimes does nothing". An agent with a shell can work through it like this: 

# Find sessions where someone hammered a control that didn't respond.
dart run picto:sessions list --has-rage-taps --limit 10

# Read one session's timeline and find the rage tap.
dart run picto:sessions timeline 3f9c2a7e

# The rage tap is at 1:42. Look at the screen around it.
dart run picto:sessions frames 3f9c2a7e --start 1:30 --end 1:50 --every 2s -o frames/

# Watch the same window as a video, with taps drawn on.
dart run picto:sessions video 3f9c2a7e --start 1:30 --end 1:50 -o checkout.mp4

The timeline is often enough on its own: it shows the screen, the taps before the rage tap and, if the app records network requests, whether the request the button made came back (see What Gets Recorded).

Limits#

Limits are per organization, per hour, over a sliding window, and rise with the plan:

PlanRenders an hourReads an hour
Invite trial5300
Starter5300
Growth151,000
Scale30Unlimited
Enterprise60Unlimited

A render is a timeline, video or frames request. An identical render that's already cached still counts, so reuse finished files. Every other request is a read: list, show, download, and each check on a running render.

Over a limit, the request fails with rate_limited and a message naming the plan's limit and how long to wait. On every plan but Enterprise the message includes a link to your organization's billing settings. The CLI exits 1; an MCP tool returns it as the tool's error. list covers every organization you can see: one at its limit is left out and the rest are served.

What the agent can see#

The agent sees what your account sees in the dashboard: sessions from organizations you own or collaborate on that have a plan or a running invite trial. list leaves out sessions from other organizations, and opening one of them directly fails with plan_required. A session from anywhere else fails as not found. The agent never sees your API keys.
