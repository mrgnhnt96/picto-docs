Uploading Assets

Save each flavor's API key with picto:setup or picto:init, and upload your app's bundled images with picto:upload_assets so replays and renders draw them.

Run dart run picto:upload_assets from your Flutter project to upload the images your app bundles, so replays and renders draw them instead of placeholders. picto:setup and picto:init save each build flavor's API key to a picto.yaml file.

A recording stores a bundled image's name, not its pixels. The dashboard can't see your app's bundle, so an image that was never uploaded draws as a placeholder. See Images.

All three commands ship in the picto package.

Prerequisites#

  • A Picto account that owns an organization. See Account & Team.
  • A Flutter project that depends on picto, with flutter pub get already run.

Save your API keys#

picto:setup signs in, lets you pick one of your organizations and a client app (or create one), and saves that app's API key under a flavor name you choose: 

dart run picto:setup

Run it again to add another flavor. It asks before replacing a flavor that's already saved, and when the file holds more than one flavor it asks whether the new one is the default. Flavor names start with a letter and contain only letters, numbers, _ and -.

If your project already declares build flavors, picto:init creates a client app for each one in a single pass: 

dart run picto:init

It finds flavors in two places:

PlatformFileWhat counts as a flavor
Android android/app/build.gradle.kts, or android/app/build.gradle Each entry in the productFlavors { } block, in Groovy ( dev { } ) or Kotlin ( create("dev") { } )
iOS ios/Runner.xcodeproj/project.pbxproj The part after the dash in a Debug-<flavor> , Release-<flavor> or Profile-<flavor> build configuration

picto:init makes one client app per flavor found on either platform, named <pubspec name>-<flavor>, such as myapp-prod, and reuses an app with that name if the organization already has one. It warns when Android and iOS list different flavors, asks before replacing a saved flavor, and asks which flavor is the default. With no flavors found, it stops and points you to picto:setup.

Both commands take --project <path> to work on a project other than the current directory.

The file they write holds one API key per flavor:

defaultFlavor: "dev"

flavors:
  dev:
    apiKey: "oc_..."
  prod:
    apiKey: "oc_..."
KeyMeaning
flavors One or more flavor names, each with the apiKey of its own client app. Required.
defaultFlavor The flavor you marked as the default. Must be one of flavors.

picto.yaml is a record for you. Your app doesn't read it: pass the key for the flavor you're building with --dart-define=PICTO_API_KEY=oc_..., as in Quick start. picto:upload_assets doesn't read the flavors either, but it stops with an error if picto.yaml exists and isn't valid.

Upload assets#

From the root of your Flutter project, run:

dart run picto:upload_assets

It asks for your email and password, lists the client apps in the organizations you own, and uploads to the ones you pick (1,3 or all). It signs in as your account, never with an API key: an API key ships inside your app, and anyone who extracts it could otherwise replace your images.

Each uploaded file prints a line, and the run ends with a count:

Done: 12 uploaded, 30 already present, 1 too large, 0 failed.

The command exits with 1 when any asset failed or it couldn't run, and 0 otherwise. A file skipped for its size isn't a failure.

FlagMeaning
--email, --password Your account. Leave either out to be prompted, which keeps the password out of your shell history.
--token An upload token instead of signing in. Also read from the PICTO_TOKEN environment variable; the flag wins. Needs --client-app-id . See Upload from CI .
--client-app-id A client app to upload to. Repeat it for several. Required with a token, and the only way to reach a client app in an organization you collaborate on but don't own.
--app-version The app version these assets ship in. Defaults to version in your pubspec.yaml . A +build suffix is dropped either way.
--on-duplicate ignore (default), override or fail . See Upload again .
--project The Flutter project to read. Defaults to the current directory.

Run it once per release, or whenever your bundled images change. Upload a version before its sessions arrive, or they show the closest earlier copy until you do.

What gets uploaded#

The command reads flutter.assets in your pubspec.yaml and nothing else, so flutter.fonts isn't uploaded.

In flutter.assetsWhat goes up
A file (assets/logo.png) The file and its density variants beside it ( assets/2.0x/logo.png ). The base file can be missing if a variant exists.
A directory (assets/images/) The files directly in it and in its density folders ( 2.0x/ , 3.0x/ ). Declare other subfolders too.
An entry with transformers: The source file, not the transformed output. A replay shows the untransformed image.
packages/<name>/<path> The file at lib/<path> in the dependency <name>.

Each file is uploaded under the name a recording uses for it, which is the asset key Flutter loads it by:

  • In an app, your own assets keep the path you declared: assets/logo.png, assets/2.0x/logo.png. Assets declared by your dependencies (not dev_dependencies), including theirs in turn, go up as packages/<name>/<path>, which is what Image.asset(..., package: '<name>') loads.
  • In a package, only its own assets go up, as packages/<name>/<path>. A project counts as a package when its pubspec sets flutter.plugin, or when it has none of lib/main.dart, web/index.html or a platform folder (android/app, ios/Runner, macos/Runner, windows/runner, linux/runner).

A replay looks an image up by that exact name in the client app the session belongs to. An image uploaded to another flavor's client app isn't found.

Dependency assets need .dart_tool/package_config.json. If it's missing, the command warns and leaves them out, so run flutter pub get in that project first.

Files over 5 MB are skipped with a warning and counted as too large, before anything is sent, and the server refuses them too. The rest of the run carries on.

Uploaded assets can be read without signing in, the same as anything in your app bundle. Don't declare a file in flutter.assets that you wouldn't ship.

If the server is busy (429 or 503), the command waits and retries each request, up to 6 attempts.

Versions#

Each client app keeps one copy of an asset per app version, so changing an image doesn't change what older sessions show. A replay picks:

  1. The copy from the version the session was recorded on.
  2. Otherwise, the newest copy from an earlier version.
  3. Otherwise, the earliest copy.

Versions compare by number, so 1.10.0 comes after 1.9.0, and build numbers are ignored: a session from 1.2.0+7 looks up 1.2.0. A session with no version shows the newest copy.

A release that didn't change an image stores nothing new: the command compares the file with the copy that version would already show, and counts a match as already present.

With no --app-version and no version in pubspec.yaml, the command says so and uploads unversioned. An unversioned copy sorts before every version.

Upload again#

Running the command again is safe. Files whose contents match what the version already has count as already present.

--on-duplicate decides what happens when the version already has the asset with different contents, such as an image you fixed without bumping the version:

ValueResult
ignore (default) Keeps the uploaded copy, warns, and counts it as already present.
overrideReplaces that version's copy. Other versions are untouched.
fail Counts the asset as failed whenever the version already has it, even with the same contents, so the run exits 1 .

Only the account that uploaded a copy can replace it. Replacing a collaborator's copy with override counts as failed.

To replace this version's copies with the files on disk, run:

dart run picto:upload_assets --on-duplicate override

Upload from CI#

In CI there's nobody to sign in, so pass an upload token and the client apps:

PICTO_TOKEN=<upload-token> dart run picto:upload_assets \
  --client-app-id <client-app-id> \
  --client-app-id <another-client-app-id>

Create the token in the dashboard:

  1. Open Account in the sidebar.
  2. Under Upload tokens, name the token after where it runs, such as GitHub Actions.
  3. Select Create token.
  4. Copy the token into your CI provider's secrets. It's shown only once.

A token acts as your account and can only upload assets to client apps you own or collaborate on. An account can hold 20 live tokens. Tokens don't expire: select Revoke beside one to stop it at once. Deleting your account revokes all of them.

Run the step after dependencies are installed, and let it fail the build: a non-zero exit means some assets didn't reach the server.

When an image still draws as a placeholder#

The browser console shows Replay: no image for "<reference>", drawing a placeholder. for each image a replay couldn't load, and a render lists them in its warnings.

CauseFix
It was never uploaded to this client app, or went to another flavor's Run the command for that client app.
It's over 5 MBMake it smaller and upload it again.
It's a network image whose URL no longer loads Nothing to upload: replays fetch it from its URL.
It has no asset name or URL: MemoryImage , FileImage , or an image a game engine decoded itself Uploading can't help. Wrap it in CaptureRealImages . See Images .

An image with no name or URL logs nothing, so a blank area with no console line can still be a missing image.
